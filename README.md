# Лабораторная работа №3 — аутентификация и авторизация

Серверная часть системы совместного редактирования документов. Ветка лабораторной: `23`.
Проект использует Express, Sequelize и PostgreSQL в Supabase. Подключение к базе берётся
из `DATABASE_URL` в существующем `.env`.

## Что реализовано и зачем

- **Модель User и миграция таблицы users.** Хранит ID, уникальный email, хеш пароля,
  роль и даты создания/обновления. Пользователи сохраняются в той же PostgreSQL, что и документы.
- **Регистрация `POST /auth/register`.** Принимает email и password, нормализует email,
  проверяет уникальность и сохраняет пароль через `bcrypt.hash(password, 10)`.
  Возвращает `201` с данными пользователя без хеша. Повторный email даёт `409`.
- **Вход `POST /auth/login`.** Проверяет пароль через `bcrypt.compare` и выдаёт подписанный
  JWT на один час с полями `id` и `email`. Неверные данные входа дают `401`.
- **Middleware auth.** Проверяет заголовок `Authorization: Bearer <token>`, подпись HS256
  и срок действия JWT. Записывает содержимое токена в `req.user`, загружает пользователя
  из базы в `req.currentUser`. Отсутствующий, неверный или истёкший токен даёт `401`.
- **Профиль `GET /profile`.** Возвращает данные текущего пользователя без пароля и хеша.
- **Защита документов.** Все маршруты `/documents` требуют авторизацию.
- **Ролевая модель RBAC — дополнительный механизм лабораторной.** Роли `user` и `admin`
  разделяют права: обычный пользователь может читать, создавать и редактировать документы,
  администратор дополнительно может удалять их. Middleware `isAdmin` возвращает `403`,
  если обычный пользователь пытается удалить документ.

При регистрации всегда назначается `user`: передача `role: "admin"` в запросе не повышает права.
Актуальная роль читается из базы на каждом запросе, поэтому изменение роли применяется
к уже выданным токенам. Удалённая учётная запись больше не может использовать свой JWT.

## Запуск с Supabase

Используется существующее подключение в `.env`. Менять `DATABASE_URL` на локальную базу
или запускать Docker не требуется. Docker Compose удалён: он создавал отдельную локальную
PostgreSQL для проверки, а проект работает с PostgreSQL в Supabase.

Добавьте в существующий `.env` секрет подписи JWT, если его ещё нет:

```dotenv
JWT_SECRET=ваш_случайный_секрет_длиной_не_менее_32_символов
PORT=7000
```

Сгенерировать секрет:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Не перезаписывайте существующий `.env` файлом `.env.example`: пример содержит только шаблон
подключения, а не ваши данные Supabase. `.env` исключён из Git.

```bash
npm install
npm run db:migrate
npm start
```

Если зависимости уже установлены, начинайте с миграций. Они создадут таблицу пользователей
в базе, указанной в `DATABASE_URL`. Для разработки можно использовать `npm run dev`.
По умолчанию сервер слушает `http://localhost:7000`.

## Маршруты и права

| Метод | Маршрут | Доступ |
|---|---|---|
| POST | `/auth/register` | Без токена |
| POST | `/auth/login` | Без токена |
| GET | `/profile` | user, admin |
| GET | `/documents` | user, admin |
| GET | `/documents/:id` | user, admin |
| POST | `/documents` | user, admin |
| PUT | `/documents/:id` | user, admin |
| DELETE | `/documents/:id` | Только admin |

## Проверка в Postman

1. Отправьте `POST http://localhost:7000/auth/register` с JSON:

   ```json
   { "email": "student@example.com", "password": "TestPassword123!" }
   ```

   Ожидаемый ответ: `201`, пользователь с ролью `user`.

2. Отправьте `POST http://localhost:7000/auth/login` с тем же JSON.
   Ожидаемый ответ: `200`, поле `token` с JWT.

3. Отправьте `GET http://localhost:7000/profile`. В разделе Authorization выберите
   Bearer Token и вставьте полученный токен. Ожидаемый ответ: `200`, данные пользователя.

4. Повторите запрос профиля без токена. Ожидаемый ответ: `401`.

5. Создайте документ через `POST http://localhost:7000/documents` с Bearer Token и JSON:

   ```json
   { "title": "Тестовый документ", "content": "Содержимое документа" }
   ```

   Сохраните ID из ответа. Отправьте `DELETE http://localhost:7000/documents/<id>`
   с тем же токеном. Ожидаемый ответ для роли `user`: `403`.

6. Назначьте зарегистрированному пользователю роль администратора:

   ```bash
   npm run set-admin -- student@example.com
   ```

   Повторите удаление с тем же токеном. Ожидаемый ответ: `204`.

Эти запросы подходят для скриншотов отчёта: регистрация, выдача JWT,
профиль с токеном и без него, отказ обычному пользователю и удаление администратором.

## Особенности реализации

JWT подписывается секретом из `.env`; сервер требует минимум 32 символа.
Пароль должен быть непустой строкой длиной до 72 байт UTF-8, поскольку bcrypt ограничивает
длину обрабатываемого пароля. Хеш и исходный пароль не возвращаются клиенту.
Уникальность email проверяется и приложением, и ограничением PostgreSQL.

Все авторизованные пользователи совместно работают с документами. Проверка владения
отдельными документами в рамках этой лабораторной не добавлялась.
